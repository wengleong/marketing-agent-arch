01 What Is Double Eddie

Double Eddie is an agentic finance ops engine that runs month-end close cycles autonomously. It uses Claude Managed Agents to coordinate specialist AI agents — document processing, transaction categorisation, reconciliation — against client data in accounting backends (BK App, Xero, QBO) and SharePoint/Dropbox.

The name: two Eddies — the AI does the grunt work, the human stays in control at review gates.

🆕
Orchestration Layer
Fastify 5 + Prisma 7 + TypeScript

Double Eddie is middleware. It creates sessions, tracks state in PG, syncs to Notion, and fires Teams alerts. Agents run in Claude's cloud — the server never processes transactions directly.

🧠
Claude Managed Agents
Sessions persist across review gates

Sessions live in Anthropic's cloud. A close run is a single long-running session — agents pause when they hit a review gate, then resume when staff resolve the exceptions.

🔗
AgentOS as Gateway
80+ MCP tools, no direct API calls

Agents never call Xero or SharePoint directly. Everything routes through AgentOS MCP tools. Double Eddie doesn't need to manage OAuth tokens.

02 Starting a Close Run

A close run moves through a clear lifecycle. Each state change is persisted to PG first, then synced to Notion.

1. Create scheduled
POST /api/close-runs
Body: clientWorkflowId, period, closeType, fyYear, fye, assignedTo, deadline.
Creates a CloseRun record in PG. Immediately creates a Notion page in the Close Tracker database — this is staff's first visibility. Page includes client name, period, backend, SharePoint link, Close Type, FY Year, FY End.
If closeType/fyYear/fye are omitted, they fall back to clientWorkflow.overrides.defaultCloseType etc.
2. Start running
POST /api/close-runs/:id/start
Updates Notion status → Running.
Resolves CloseManager agent ID from AgentConfig DB table.
Builds a 4-layer prompt:
  1) Base: "Execute the monthly close workflow."
  2) Workflow instructions: template name + steps JSON
  3) Client overrides: clientWorkflow.overrides JSON
  4) Backend context: backend, bkappCompanyId, Close Type, FY Year, FY End
Attaches memory stores: client-specific (read/write) + firm-wide (read-only).
Calls ManagedAgentRuntime.startSession() → Anthropic client.beta.sessions.create().
Sends initial task as user.message.
Launches async processEvents() loop — API returns immediately.
3. Session running — event stream
processEvents() iterates streamEvents() — async for-await over Managed Agents SSE:
  • agent.message → written to EventLog; last message tracked for exception context
  • session.thread_status_idle + requires_action → triggers review gate
  • session.thread_status_idle + end_turn → marks complete, sends Teams summary
4. Review Gate awaiting_review
Agent emits requires_action. SessionManager:
  1) Creates Exception row in PG (step, agent, description from last message)
  2) Creates Notion exception queue row (linked to close run page)
  3) Updates Notion close run status → Awaiting Review, increments exception count
  4) Sends Teams alert to configured channel
Session stays paused. Staff review in Notion.
5. Staff resolves exceptions
PUT /api/exceptions/:id/resolve
Staff sets decision: approved / overridden / dismissed + staffDecision note.
Syncs to Notion exception row (status + Staff Decision field).
When 0 pending exceptions remain → SessionManager.resumeClose() fires automatically.
6. Auto-resume running
Collects all staff decisions into a StaffDecision[] summary.
Sends user.message to paused session: "Staff review complete. Decisions: [...]"
processEvents() loop restarted. Close run status → running.
Session resumes from exactly where it paused.
7. Complete complete
Agent emits end_turn. SessionManager marks PG record complete, updates Notion → Complete.
Sends Teams completion message: client, period, duration, exception count resolved.

03 Notion Setup — FE / BE Split

Notion is the staff-facing frontend. PostgreSQL is the source of truth. Every Notion write is a best-effort sync from PG — if Notion goes down, PG holds all state and the close continues. Staff can force a resync at any time.

Setup: one-time (already done) Run NOTION_PARENT_PAGE_ID=<page_id> npx tsx scripts/setup-notion.ts once to create all 4 databases. The resulting database IDs are stored as env vars.

Resync — recovering from Notion outages

🔁
API endpoint
POST /api/close-runs/:id/resync-notion

Re-syncs one close run + all its exceptions from PG → Notion. Creates pages that are missing, updates pages that exist. Returns { synced, notionPageId, exceptionsSynced, exceptionErrors }.

💻
CLI script
# All active runs (excludes scheduled)
npx tsx scripts/resync-notion.ts

# One specific run
npx tsx scripts/resync-notion.ts --run-id cr_abc

# Everything including completed
npx tsx scripts/resync-notion.ts --all
Notion failure policy Synchronous API paths (POST, start, exception resolve) include a notionError or notionSyncError field in the response if Notion sync fails. Async event paths (review gate, completion) cannot return HTTP errors — instead they send a Teams notifyError alert so staff know to check the system DB directly. PG is always written first.

claude-sonnet-4-6
Specialist
Role

Fetches documents from client Dropbox/SharePoint folders, classifies each (invoice, receipt, bank statement, contract, payslip, unknown), routes to the correct system.

Bank statement workflow

1. List files → 2. dropbox_create_shared_link + ?dl=1 → 3. bkapp_upload_statement (AgentOS fetches & uploads multipart) → 4. Confirm via bkapp_list_statements

Confidence threshold

Any doc it cannot classify with confidence > 0.7 is flagged as an exception for human review.

📈
CategorizationAgent
claude-sonnet-4-6
Specialist
BK App workflow (6 steps)
  1. Call bkapp_get_coa → load Chart of Accounts
  2. Call bkapp_list_transactions(filter=needs_review) → fetch uncategorized transactions (paginate)
  3. For each: check memory store for known vendor mappings
  4. Call bkapp_update_transactions in batches with category + confidence + rationale
  5. Confidence < 0.5 → do NOT write, flag as exception instead
  6. Report summary: total processed, auto-categorized, flagged
Confidence routing
≥0.8 auto-categorize 0.5–0.79 flag for review <0.5 exception

Memory Architecture

🧠
Client Memory Store
Per-client · Read/Write

Attached to each session via clientWorkflow.memoryStoreId. Agents write vendor mappings, quirks, and categorization learnings back after each close. These persist across monthly runs — the agent gets smarter over time without manual updates.

⚠ Not yet provisioned: All 64 ClientWorkflow rows have memoryStoreId = null. Until memory stores are created and linked, every close run starts with no memory — the agent re-learns from scratch each month. Use MemoryManager.createStore() per client and save the ID to PG before the first live run.

📚
Firm Memory Store
Shared · Read-Only

Attached to all sessions via FIRM_MEMORY_STORE_ID env var. Contains firm-wide accounting standards, SFRS rules, GST treatment rules. All agents reference it but cannot write to it.

06 Categorization: Two Separate Pipelines

Key architectural nuance There are two independent categorization systems that both write to the same BK App transaction table. They don't talk to each other — they cover different scenarios.

BK App Built-In Pipeline

TriggerHuman uploads statement in BK App UI
RuntimeAgent SDK query() inside BK App Node.js process
AgentsCategorizationAgent → EvalAgent → (LearningLoopAgent post-close)
ContextVendor mappings, GL history, correction rules from BK App DB
LearningLearningLoopAgent proposes vendor map promotions + corrections (PENDING_HUMAN_REVIEW)
OutputWrites to BK App Transaction table directly

Double Eddie Pipeline

TriggerCloseManager dispatches as a workflow step
RuntimeClaude Managed Agents — runs in Anthropic's cloud
AgentsCategorizationAgent (Managed Agent with memory store)
ContextManaged Agents memory store (persists vendor mappings across months)
LearningWrites learnings back to memory store automatically — no approval needed
OutputWrites via PATCH /api/companies/:id/transactions with service auth

How they co-exist without double-writing

The BK App's built-in pipeline runs first (on upload). Double Eddie's agent only picks up transactions that the BK App pipeline didn't resolve with confidence — it queries with filter=needs_review, which returns: status != 'reviewed' AND (confidence < 0.85 OR confidence IS NULL). So there's no double-write: BK App categorizes what it can, Double Eddie cleans up what's left.

The learning gap (watch-out)

Two isolated learning loops — not reconciled yet BK App's LearningLoopAgent generates vendor map promotions and correction rules stored in the BK App DB. Double Eddie's agent writes learnings to the Managed Agents memory store. Neither feeds the other. If you use both systems for the same company, their learning diverges over time. A future integration task: either (a) expose BK App vendor maps via a bkapp_get_vendor_mappings tool that Double Eddie reads at start of each run, or (b) push BK App's approved learning proposals into the Managed Agents memory store.

BK App's 3-agent categorization pipeline (detail)

1
CategorizationAgent
claude-sonnet-4-6 · Agent SDK
  • Runs in batches of 30 transactions
  • Checks vendor mappings (hard rules, 100% confidence) first
  • For unknowns: uses web search to identify vendor
  • Assigns COA code + confidence + rationale per transaction
  • Returns vendorResolved flag if web search was needed
2
EvalAgent
claude-haiku-4-5 · cheaper
  • Calibrates confidence scores from pass 1
  • Compares against vendor history (prior period accuracy)
  • Sets needsReview flags
  • Final confidence ≥0.85 → auto-approved in UI
3
LearningLoopAgent
claude-sonnet-4-6 · post-close only
  • Runs after an accountant approves a period
  • Analyses closed-period transactions vs final assignments
  • Proposes: vendor map promotions (3+ consistent correct), correction rules (2+ same mis-category)
  • All proposals are PENDING_HUMAN_REVIEW — accountant approves before applying

10 Chaser Bot — Inbox Manager Integration Future Build

When CloseManager discovers a document is missing, it should be able to chase the client directly through the Grof Inbox Manager chaser system — without waiting for a human. The agent decides when to chase; staff are notified but don't need to act.

Inbox Manager chaser system (existing)

💌
ChaseChain
One chain per outstanding item
  • Strategy: gentle (3/7/14/21/30 days), firm (2/5/10/17/25), urgent (1/3/7/12/18)
  • Up to 20 steps per chain
  • Approval modes: approve_each, auto, first_only
  • Auto-stop on reply or attachment
  • ChaseStepAgent writes the draft email/message
🔍
Response Detection
Auto-stops chain when resolved
  • chaser-response-detector inspects replies for document received / confirmed / resolved signals
  • Attachment detection: chain stops when the awaited file arrives
  • Cron checks chains every N minutes for next scheduled step

11 Watch-Outs

🚫
sync-agents must run before first start

If AgentConfig has no row for CloseManager with a valid managedAgentId, POST /:id/start returns 500. Run npx tsx scripts/sync-agents.ts first.

🔔
Notion failures don't stop the close

If Notion is unreachable during async events (review gate, completion), staff will not see the job update. They'll get a Teams error alert instead. Always use resync-notion after an outage. PG is always the source of truth.

📈
Dual categorization pipeline

BK App's built-in pipeline runs first on upload. Double Eddie's agent only picks up needs_review transactions. If both run for the same company, their learning systems are isolated — see Section 6.

🏭
Managed Agents beta access required

The Anthropic API key must have Managed Agents beta access enabled (anthropic-beta: agents-2025-05-15). Check in Claude platform console under Org Settings → Beta programs. Without it, session create returns 403.

🔐
Three Railway env vars needed
  • BK App: BK_INTERNAL_API_KEY
  • AgentOS: BK_INTERNAL_API_KEY (same value) + BK_APP_URL
  • Both must match — service auth uses exact key comparison
🧠
Memory store must exist before first run

Each ClientWorkflow should have a memoryStoreId. Create it via Managed Agents API before scheduling the first close. If missing, the session runs without client memory — the agent will re-learn from scratch every month.

📌
Session resume requires active session

If the Managed Agents session expires before staff resolve exceptions, resumeClose() will fail. Session lifetime needs to be confirmed for long-running review gates (multi-day review periods).

📄
DocumentAgent needs Dropbox path in overrides

The agent knows to list dropbox_list_folder — but it needs to know the path. This should be in clientWorkflow.overrides.dropboxFolderPath or injected in the backend context. Without it, the agent will try to guess.

Memory architecture — how memories carry across monthly closes

Each ClientWorkflow has one memoryStoreId (Anthropic Managed Agents memory store). The same store ID is attached to every session for that client. After each close, CategorizationAgent writes vendor mappings and learnings back into the store. The next month's close picks them up automatically — no manual work.

One CloseManager coordinator per close run (isolated session). Multiple clients can close in parallel — each gets its own session and memory store attachment. There is no cross-client memory leakage.
